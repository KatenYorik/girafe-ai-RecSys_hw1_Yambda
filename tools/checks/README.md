# Проверки EDA

Каждый скрипт принимает путь к `data/raw` и печатает отчёт:

```bash
python -I tools/checks/c0_verify.py data/raw
```

## Блок 01 — санити

| Скрипт | Что считает |
|---|---|
| `c0_verify.py` | строки и схемы всех файлов, сверка с карточкой |
| `c0_items_union.py` | треки и пользователи по типам событий и по объединению |
| `c0_coverage.py` | покрытие артистами, альбомами, эмбеддингами; фиты |
| `c1_dupes_nulls.py` | пропуски, дубли по ключу и полные дубли |
| `c2_dup_detail.py` | распределение повторов внутри ключа |
| `c3_ratio_length.py` | `played_ratio_pct` и `track_length_seconds` |
| `c4_time.py` | окно, точка отсчёта, прослушивания по дням, сортировка |
| `c5_organic.py` | смысл `is_organic`: доли, завершаемость, динамика |
| `c6_like_state.py` | лайк/анлайк как состояние, анлайки без лайка |

`c0_coverage.py` ждёт в `data/raw/` файл `embed_item_ids.parquet` — колонку `item_id` из удалённого
`embeddings.parquet`, см. [`data/README.md`](../../data/README.md).

## Блок 02 — время

| Скрипт | Что считает |
|---|---|
| `t1_time_unit.py` | единица `timestamp`: сетка значений, суточный период, интервал между соседними прослушиваниями против длины трека; пересчёт принятых границ в реальные сутки |
| `t2_seasonality.py` | поток по реальным суткам, внутрисуточный профиль, недельная сезонность (сырая и детренд), фаза недели на границах окон, провалы и скачки, разбор «дня 195» блока 01 |
| `t3_windows.py` | метрики окна для test длиной 7…90 реальных суток и для val 7…90 суток перед ним: оцениваемые пользователи, релевантные новинки, цена для train |
| `t4_final_split.py` | **числа по принятому сплиту** (train 0…258 / val 259…279 / test 280…300): объёмы, оцениваемые, распределение новинок, три ступени новизны, срез «новый артист», разрез по `is_organic` — отдельно для test и для val |

**Важно:** `t1_time_unit.py` показал, что единица `timestamp` — **1 секунда**, а не 5, то есть
сутки = 86400 единиц, а не 17280. Скрипты блоков 01, 05 и 06 продолжают использовать
`DAY = 17280`, чтобы их числа воспроизводились; в каждом таком скрипте сверху стоит пометка,
а все горизонты, которые они печатают «в днях», читаются как `дни / 5` реальных суток.
Помечены: `c4_time.py`, `c5_organic.py`, `n1`…`n4`, `s1`…`s6`. Тексты блоков 01, 05 и 06
пересчитаны в реальные сутки 21.10.2026.

## Блок 04 — треки и артисты

Каталог везде считается **только по истории до test** (сутки 0…279) и по пулу пользователей
блока 03: каталог, построенный с участием тестового окна, был бы утечкой в метрику.

| Скрипт | Что считает |
|---|---|
| `i1_item_dist.py` | хвост популярности треков и артистов, сколько треков покрывают 50/80/90/95 % прослушиваний, пороги по числу слушателей и какой порог даёт каталог нужного размера |
| `i2_catalog_rule.py` | три правила задания каталога (топ-K в подвыборке / порог по доле слушателей / фиксированный каталог пула) и устойчивость каталога к сиду подвыборки |
| `i3_catalog_artists.py` | внутри принятой конфигурации: покрытие метаданными, артисты каталога, срез «новый артист» с ограничением каталога и без него |

## Блок 07 — холодные треки

| Скрипт | Что считает |
|---|---|
| `h1_cold_items.py` | доля релевантных новинок на треках без истории до test и их эмбеддинги; сколько таких треков попадает в каталог; две переформулировки среза — «молодые» треки каталога и нижняя полоса каталога по популярности |
| `h2_cold_slice_price.py` | слабеет ли коллаборативный сигнал у молодых треков каталога; цена расширения каталога холодной полосой (пары, бюджет, достижимые новинки); обучающий сигнал в холодных полосах |
| `h3_new_releases.py` | срез «недавние релизы»: размер и пригодность при шести порогах новизны, подробности по выбранному порогу (популярность, обучающий сигнал, эмбеддинги, органика) и пересечение со срезом по новым артистам (таблица 2×2). Порог новизны — второй аргумент, по умолчанию 200 |

## Блок 08 — симуляция подвыборки

| Скрипт | Что считает |
|---|---|
| `b1_seed_stability.py` | проверка на утечки тестового окна; устойчивость подвыборки к сиду (пары, плотность, оцениваемые, `k >= 10`, достижимые новинки, оба среза); запас по бюджету при разных N; несмещённость случайного отбора против пула |

Саму подвыборку собирает не проверка, а
[`tools/build_subsample.py`](../build_subsample.py) — он детерминированно материализует
`data/subsample/` (train / val / test, каталог, пользователи) и печатает отчёт по объёмам.

## Блок 09 — признаки для FM и защита от утечек

Каждый признак считается по окну `ts < W` и собирается дважды: `W = VAL0` (train, сутки 0…258 —
для подбора гиперпараметров на val) и `W = TEST0` (train+val, сутки 0…279 — для финальной
модели). Тестовое окно не участвует ни в одном признаке.

| Скрипт | Что считает |
|---|---|
| `f1_item_features.py` | признаки трека на каталоге: сколько треков входят в несколько альбомов и три правила выбора одного (однозначность, согласие правил, насколько альбом вообще группирует каталог); покрытие эмбеддингами, их размерность и норма; популярность, завершаемость, органика и возраст трека по двум окнам с квантилями; расхождение популярности между окнами (сдвиг ранга, пересечение топов, Спирмен); артист как признак |
| `f2_user_features.py` | 15 агрегатов пользователя на подвыборке из 3 000 по двум окнам: квантили, доля пользователей с неопределённым значением, расхождение train против train+val (прирост медианы, медиана сдвига, корреляция), доля особенно подвижных пользователей и пустые случаи (нет истории в train, нет лайков, нет дизлайков) |
| `f3_leakage_audit.py` | аудит утечек: структурная проверка источников на наличие `timestamp`; каждый признак трека и пользователя посчитан по окну и по всем данным — сколько сущностей изменилось бы и насколько; цена утечки в признаке «трек/артист знаком» (целевые пары, доля кандидатов); лайки по окнам и состояние лайка на границе теста против итогового с таблицей переходов; лайк без прослушивания; список набора с окном каждого признака |
| `f4_export_embeddings.py` | выгружает векторы 10 000 треков каталога из удалённого `embeddings.parquet` (13,8 ГБ) в `data/catalog_embeddings.parquet` во `Float32` — **сделано: 9 675 векторов, 9,2 МБ, 15 минут**. Читает чанками по строкам (`slice` проталкивается в сканирование и пропускает лишние row group'ы), качает только `embed` и нормирует локально, предварительно проверив на выборке, что `normalized_embed = embed/‖embed‖`; каждый чанк пишется отдельным файлом и при повторном запуске не перекачивается. Аргументы: путь к `raw`, путь вывода, размер чанка (по умолчанию 800 000) |
| `f5_like_provenance.py` | из чего состоит лайк: реакция на звук против внешнего канала; разрыв лайк → прослушивание |
| `f6_premature_likes.py` | преждевременные лайки: популярность артиста, знакомство, пресейвы, залпы |
| `f7_known_asymmetry.py` | асимметрия «знаком / релевантен»: сколько «знакомых» треков не слышали и сколько целевых пар теряем |
| `f8_mass_likers.py` | массовые лайкеры: профиль группы, вклад в лайки, влияние на метрику и признаки |
| `f9_like_rate.py` | скорость лайков против скорости прослушивания: откуда брать порог массового лайкера |

## Блок 05 — сигналы для таргета

Все шесть скриптов считают только по train (дни 0…1413, `timestamp < 1414 * 17280`; граница
задана константой `TRAIN_DAYS` в начале каждого скрипта), чтобы
пороги и коэффициенты таргета не подбирались с участием тестового окна.

| Скрипт | Что считает |
|---|---|
| `s1_played_ratio.py` | распределение `played_ratio_pct` мелким шагом в зонах 0–20 % и 90–100 %, плотность по зонам, пороги, та же зона скипов в секундах |
| `s2_organic_within_item.py` | завершаемость у органики и рекомендаций: сырое сравнение, внутри одного трека (пулинг и парно), контроль популярности |
| `s3_repeats.py` | распределение числа прослушиваний пары, хвост, цена усечения `min(n, C)`, завершаемость против числа повторов, растянутость по времени |
| `s4_first_listen.py` | влияние первого прослушивания на P(повтор), E[n], P(like), P(dislike); P(like \| n) с приростом на повтор; совместная таблица |
| `s5_like_prob.py` | P(like) по `played_ratio` первого прослушивания мелким шагом; проверка аномалии 99–100 % на органику и длину трека; P(like) по максимуму пары |
| `s6_like_stability.py` | отмены лайка: частота, задержка в днях, доля отмен за H дней с поправкой на цензуру; дизлайки и их снятие; прослушивания после анлайка |

## Блок 06 — новизна

| Скрипт | Что считает |
|---|---|
| `n1_test_window.py` | по окнам test 7/14/30/60/90 дней: сколько пользователей оцениваем (есть ≥ 1 релевантный новый трек) и сколько у них релевантных новинок |
| `n2_novelty_tiers.py` | три ступени новизны (знакомый трек / новый трек знакомого артиста / новый артист), срез «новый артист», разрез по `is_organic` |
| `n3_censoring.py` | левая цензура: новизна по дню первого прослушивания, зависимость от длины train-истории, псевдо-цензура |
| `n4_window_timing.py` | когда внутри окна случаются релевантные новинки; цена окна для train |

## Блок 03 — пользователи

| Скрипт | Что считает |
|---|---|
| `u1_user_dist.py` | распределения прослушиваний, треков, активных суток и плотности активности на пользователя; концентрация в верхних процентах; первые сутки пользователя; активность в train/val/test; пороги по активности; доля `played_ratio == 0` |
| `u2_anomalies.py` | три вида аномалий: повторы одного трека в одну секунду («боты» блока 01), почти круглосуточная активность, перелистывание; проверка, сдвинут ли профиль у «ночных» пользователей (часовой пояс) или размазан |
| `u5_catalog_bands.py` | что несут полосы каталога по популярности (треков, взаимодействий, сколько пользователей знают трек), потолок метрики по размеру каталога (сколько людей имеют k ≥ 1/3/5/10 достижимых новинок) и доля релевантных новинок, достижимых внутри каталога; принимает N вторым аргументом |
| `u4_subsample_grid.py` | предельное N при бюджете 2 млн пар для каталогов топ-3/5/8/10/15 тыс. и «весь»; по конкретным конфигурациям — пары, плотность, оцениваемые, доля оцениваемых, отрезанных каталогом, покрытие взаимодействий и память под матрицу EASE |
| `u3_funnel_subsample.py` | воронка фильтрации пользователей для обеих версий границ; цена порога по активности в оцениваемых; пары (пользователь, трек) и плотность матрицы при N = 1000…все и каталоге топ-5/10/15 тыс. треков |
